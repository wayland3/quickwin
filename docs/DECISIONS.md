# 架构决策记录（ADR）

格式：编号 · 标题 · 状态 · 背景 · 决策 · 代价 · 替代方案。
状态取值：`已采纳` / `待定` / `已废弃` / `后置`。

## ADR-0001 使用 Tauri 2 而非 Electron

**状态**：已采纳（2026-10-25）

**背景**：需要常驻后台、全局热键、剪贴板历史、低资源占用。候选为 Electron、Tauri、WPF。

**决策**：Tauri 2 + Rust 后端 + React/TS 前端。

**理由**：

- 安装包与内存显著小于 Electron（常驻场景收益明显）。
- 本机已具备 MSVC Build Tools 与 WebView2，仅缺 Rust 工具链，补齐成本低。
- Rust 直接调 Win32 比 Node 原生模块链路更可控，也不需要 `node-gyp`。

**代价**：

- Rust 学习与编译时间；首次构建慢。
- 前端调试与 Rust 调试分离，需要两套日志。
- 生态与现成轮子少于 Electron。

**替代方案**：

- Electron：迭代最快，但常驻内存 100MB+，与「轻量」目标冲突。
- WPF/.NET：Windows 集成最好，但 Web 化 UI 与打包流程弱，且本机未装 SDK。

## ADR-0002 Win32 调用全部由 Rust `windows` crate 承载

**状态**：已采纳

**背景**：需要 `SendInput`、剪贴板多格式读写、前台窗口与焦点恢复、`RegisterHotKey`。可选方案：Node FFI（koffi/robotjs）、Rust `windows` crate、PowerShell 脚本。

**决策**：只用 `windows` crate，集中封装在 `src-tauri/src/platform/`。

**理由**：

- 类型安全、错误码可映射、无额外运行时依赖。
- 剪贴板/焦点/输入需要紧密配合（同一线程、同一套句柄），放在同一语言层最省心。
- 避免 `robotjs` 这类停维护或需编译的 Node 原生模块。

**代价**：

- 需要写 `unsafe` 与 SAFETY 注释。
- `windows` crate feature 较多，需要按需裁剪控制编译时间。

**替代方案**：

- PowerShell `SendKeys`：慢、不可靠、无法处理 Unicode 与焦点。
- 低级键盘钩子：杀软敏感、稳定性差，明确不做。

## ADR-0003 SQLite（rusqlite bundled）+ blob 文件

**状态**：已采纳

**背景**：剪贴板历史需要去重、全文搜索（含中文）、TTL 清理、置顶、来源信息；图片需要磁盘存储。

**决策**：

- 结构化数据与文本存 SQLite（`rusqlite`，`bundled` 自带 SQLite 与 FTS5）。
- 图片/缩略图存 `blobs/` 文件，DB 只存相对路径。
- 独立 FTS5 表（非 external content），写入时同步。
- 去重键用 `sha2`（`Sha256`）计算 `sha256(kind + 规范化内容)`，避免引入更大体积的加密库。

**理由**：

- 一次查询解决过滤/排序/分页/TTL；无需把 1 万条读进内存。
- FTS5 trigram 支持中文子串，避免 `LIKE '%词%'` 全表扫描。
- WAL + 单写线程可稳定承受 200 次/天的写入。
- `bundled` 不依赖系统 SQLite，用户机器无需额外安装。

**代价**：

- 首次编译 30–60 秒；二进制增大约 1MB。
- 需要维护迁移与迁移测试。
- 独立 FTS 表多存一份文本（15 天数据量下可忽略）。

**替代方案**：

- JSON/JSONL：图片少时够用，但搜索、TTL、崩溃恢复都要手写，长期成本更高。
- sled/redb：纯 Rust 无 SQL/FTS，索引全手写，调试工具少。
- 图片存 BLOB：备份简单，但 DB 体积膨胀、VACUUM 昂贵。

## ADR-0004 剪贴板保留策略

**状态**：已采纳

**背景**：需求为「最多保存 15 天」，但需要明确按哪个时间、置顶如何处理、如何防磁盘膨胀。

**决策**：

- TTL 15 天，按 `last_copied_at`（最后一次使用）计算，不是 `created_at`。
- 置顶项豁免 TTL 与自动淘汰。
- 硬上限：10,000 条；单文本 256KB；单图 8MB；blob 总量 500MB。
- 清理时机：启动 + 每 6 小时 + 每 200 次写入；清理后回收孤儿 blob。

**理由**：

- 按最后使用计算符合直觉：每天用的条目不会在第 16 天突然消失。
- 用户主动置顶即表达「长期保留」意图，自动删除会造成数据丢失。
- 上限防止「复制大文件/大量截图」把磁盘写满。

**代价**：

- 置顶项可能长期占用空间，需要设置页展示占用并提供手动清理。
- 清理是批量操作，极端情况下会短暂阻塞写入（已在事务内限制批量大小）。

**替代方案**：

- 按创建时间：实现简单，但常用条目会被误删。
- 分类不同 TTL（文本 7 天/图片 3 天）：规则复杂，v1 不做。

## ADR-0005 从历史激活不污染历史

**状态**：已采纳

**背景**：需求原文「下次粘贴的就是它，但这次选择不污染剪贴板历史」。需要明确「污染」指什么。

**决策**：

- 激活条目时写系统剪贴板并发送 `Ctrl+V`，**不新增历史条目、不改变历史顺序**。
- 条目保留在系统剪贴板（与 Win+V 行为一致），便于用户再次手动粘贴。
- 监听线程用「内容 hash + 1.5 秒窗口」抑制本次写入。
- 提供可选设置「粘贴后还原原剪贴板」（默认关闭）。

**理由**：

- 「不污染」指历史，不是系统剪贴板；保留条目让「下次粘贴就是它」成立。
- 不重排可避免用户刚选过的条目突然跳到顶部造成困惑。

**代价**：

- 用户原本的剪贴板内容会被覆盖（与所有剪贴板管理器一致）。
- 抑制窗口是启发式的，极端情况下仍可能重复入库，需要 hash 去重兜底。

**替代方案**：

- 粘贴后立即还原原剪贴板：更「礼貌」，但与「下次粘贴就是它」冲突，且还原可能丢失富格式。
- 每次激活新增一条历史：会快速刷屏，明确不做。

## ADR-0006 剪贴板监听用序列号轮询

**状态**：已采纳（可在有性能证据后升级）

**背景**：`AddClipboardFormatListener` 需要隐藏窗口与消息循环；轮询实现简单但可能有延迟与 CPU 开销。

**决策**：250ms 轮询 `GetClipboardSequenceNumber()`，变化后延迟 30ms 读取；失败重试 5×20ms。

**理由**：

- 读序列号是极轻量调用，无变化时 CPU 占用接近 0。
- 不需要额外窗口、线程消息循环与窗口类注册，减少与 Tauri 窗口体系的耦合。
- 30ms 延迟躲开「源应用尚未写完」的竞态，实践中足够。

**代价**：

- 最坏 250ms 延迟；复制后立刻按 `Alt+V` 可能看不到最新一条（需要手动刷新）。
- 极端高频复制（自动化脚本）可能合并事件。

**替代方案**：

- `AddClipboardFormatListener`：延迟更低，但需要窗口 + 消息循环 + 生命周期管理。
- 升级条件：若实测延迟影响使用，另开 ADR 切换并补测试。

## ADR-0008 单浮层窗口 + mode 切换

**状态**：已采纳

**背景**：两个功能都需要一个居中浮层；可以做成两个窗口或一个窗口两种内容。

**决策**：一个 `overlay` 窗口，按 `mode` 渲染不同视图；设置窗口独立。

**理由**：

- 避免多窗口焦点竞争与「显示哪个」的调度复杂度。
- 尺寸动态调整，切换模式即切换内容，视觉一致。
- 内存与启动开销更小。

**代价**：

- 模式切换需要清理各自状态（搜索词、滚动位置）。
- 单窗口内的错误边界更大，一个渲染错误影响全部模式。

**替代方案**：

- 多窗口：隔离性好，但焦点/层级/预热窗口管理复杂，收益不足。

## ADR-0009 FTS5 独立表 + LIKE 回退

**状态**：已采纳

**背景**：需要中文子串搜索。FTS5 的 `unicode61` 分词对中文不友好；`trigram` 支持子串但要求查询 ≥3 字符。

**决策**：

- 建独立 `clipboard_fts(preview, text_body, tokenize='trigram')`，rowid 与主表 id 一致。
- 写入/删除时在同一事务内同步，不用触发器。
- 查询 <3 字符时回退 `LIKE`（`preview` + `text_body`）。

**理由**：

- trigram 让中文 3 字以上查询走索引，性能与排序（bm25）都更好。
- 独立表避免 external-content 的触发器同步 bug，多存一份文本可接受。
- 短查询回退 `LIKE` 在 1 万条规模下仍 <50ms。

**代价**：

- 双写，需保证事务一致；测试必须覆盖「删主表不删 FTS」的回归。
- 查询串需要转义双引号，避免 FTS 语法注入导致报错。

**替代方案**：

- `unicode61` + 自建分词：中文效果差，维护成本高。
- 纯 `LIKE`：实现最简，但 1 万条全文扫描接近预算上限。

## ADR-0012 不修改系统前台锁与输入法设置

**状态**：已采纳

**背景**：为了让焦点恢复更可靠，有人会改 `SPI_SETFOREGROUNDLOCKTIMEOUT` 或注册低级键盘钩子。

**决策**：不修改任何系统级设置，不使用全局键盘钩子；焦点恢复失败就提示用户。

**理由**：

- 修改系统设置会影响其他程序，用户卸载后无法自动还原。
- 低级钩子易被杀软判定为键盘记录器，且会拖慢全系统输入。
- 失败可提示、可手动操作，代价远小于系统级副作用。

**代价**：

- 少数场景焦点恢复失败（如某些全屏应用），需要用户手动点击。
- 无法实现「双击 Ctrl 唤起」这类需求（v2 若要，需重新评估）。

## ADR-0013 启用 Tauri `protocol-asset` feature 加载 blob 图片

**状态**：已采纳（T-204）

**背景**：剪贴板图片预览需要让 WebView 直接读取 `%APPDATA%\com.quickwin.app\blobs\` 下的文件。
UI-SPEC §10 禁止 base64 内联；Tauri 2 提供 asset 自定义协议。

**决策**：

- `src-tauri/Cargo.toml` 的 `tauri` 增加 `protocol-asset` feature。
- `tauri.conf.json` 开启 `security.assetProtocol.enable`，scope 为 `"$APPDATA/blobs/**"`。
- 二者缺一不可：只开配置不会注册协议处理器（源码里由 `#[cfg(feature = "protocol-asset")]` 门控），
  只开 feature 不会放行路径。

**理由**：

- `$APPDATA` 解析为 `app_data_dir()` = `dirs::data_dir()/identifier`，已经包含 identifier；
  scope 若再写一层 `com.quickwin.app` 会双重目录，`is_allowed` 恒 false（403）。
- 不是新增 crate，只是启用既有依赖的 feature，因此不新开 ADR 之外的依赖决策。

**代价**：

- 引入传递依赖 `http-range`（Tauri 官方默认组合，非自选）。
- 需要保持 `storage.rs` 落盘目录与 scope 一致，二者任一变更都要同步改。`

## ADR-0014 v1 schema 只包含剪贴板表，其余表按里程碑迁移

**状态**：已采纳（2026-10-29，T-106 评审 C2）

**背景**：`ARCHITECTURE §5.2` 原把 `meta / clipboard_item / clipboard_fts / app_index / usage_stat / settings` 全部列为 v1 schema；实际 v1 只实现了剪贴板两张表。若应用发布后再把剩余表补进 SCHEMA_V1，会违反「禁止修改已发布 migration」。

**决策**：
- v1 migration（user_version=1）只包含 `clipboard_item` 与 `clipboard_fts`，不再变更；
- `meta / app_index / usage_stat / settings` 随对应功能（M3 / M6）以独立 migration（v2+）落地；
- `ARCHITECTURE §5.2` 已补版本归属说明，完整 SQL 仅作结构参考。

**理由**：
- 应用尚未发布，现在明确版本归属成本最低；
- 每张表与具体里程碑绑定，迁移顺序与功能上线顺序一致；
- 避免空表提前占用 schema，又在需求变化时被迫改迁移。

**代价**：
- 后续里程碑各需新增 migration 与迁移测试（本就属于硬规则）；
- 文档中的完整 schema 与单版本实际结构不同，必须靠版本说明消除歧义。

## ADR-0017 直接依赖 `global-hotkey` 以获得类型化热键错误

**状态**：已采纳（2026-11-02，用户确认）

**背景**：T-607 需要在设置页实测「某个组合键当前是否可用」。要精确区分两种情况：

- **被占用**：该组合键已被系统或其他程序 grab（Windows 上 `RegisterHotKey` 返回 `ERROR_HOTKEY_ALREADY_REGISTERED`；X11 上 `grab_key` 返回 `Access` 错误）
- **探测失败**：探测环境本身不可用（X11 连接断开、权限不足等）

现有依赖 `tauri-plugin-global-shortcut` 把底层 `global_hotkey::Error` 降级成了扁平字符串
（`Error::GlobalHotkey(String)`），两种情况混在一起，只能靠匹配英文错误文案来区分
（`"HotKey already registered"`），上游改文案即失效。

**决策**：在 `src-tauri/Cargo.toml` 中把 `global-hotkey = "0.8"` 声明为**直接依赖**，
热键探测改用 `global_hotkey::GlobalHotKeyManager` + 类型化的 `Error::AlreadyRegistered`。

**理由**：

- `global-hotkey` 本就是 `tauri-plugin-global-shortcut` 的传递依赖，版本完全一致（0.8.0），
  **不引入新包、不增加编译量、不改变依赖树**；
- 标准库与既有依赖（插件）都无法提供类型化的「已被占用」信号 —— 插件已经把它拍平了；
- 字符串匹配错误文案是脆弱耦合，且本项目要求错误信息稳定可预期。

**代价**：

- 多一条直接依赖边，需在实现备注中说明理由；
- 探测逻辑绕过插件，直接用底层 crate，与运行时绑定使用不同的 manager
  （因此探测不会与运行时绑定互相干扰，见 T-607 实现备注）。

**替代方案**：

- 匹配插件错误字符串前缀：零新增依赖，但耦合上游英文文案，改动即失效；
- 只在「注册成功/失败」二分，不区分占用与故障：用户会看到误导性提示
  （例如 X11 断开时提示「已被其他程序占用」）。
