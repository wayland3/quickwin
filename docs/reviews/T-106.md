# T-106 SQLite 存储层

**实现模型**：随 T-201～T-205 分阶段实现（未单独记录单一模型）
**评审模型**：GLM-5.3
**评审日期**：2026-10-29
**结论**：PASS（条件复核后最终 PASS）

## 评审过程

- 第 1 轮：**PASS（附条件）**，三个风险：
  1. `check_fts_consistency` 两条 COUNT 非同快照，且每次写命令 open 都全表扫描，可能误触发 rebuild；
  2. v1 实际 schema 与 ARCHITECTURE §5.2 不一致（只建了剪贴板两表），后续有「改已发布迁移」风险；
  3. busy_timeout 设置晚于 journal_mode 切换，并发首开可能拿到硬 SQLITE_BUSY；
     并发测试只做了 100 写 + 20 查，未对齐验收字面。
- 修复：
  1. 一致性检查改为单语句单快照；新增 `open_write_at` 跳过计数检查，写命令改用，校验只在启动执行；
  2. ADR-0014：v1 只含 `clipboard_item` / `clipboard_fts`，其余表随 M3/M4/M6 走 v2+ migration；
     ARCHITECTURE §5.2 补版本归属说明；
  3. busy_timeout 提前到 configure 第一步；并发测试改为 100 写 + 100 查。
- 第 2 轮：**PASS**，所有条件核实通过；要求评审记录落盘（本文件）。

## 验收核对

- WAL / busy_timeout=5000 / foreign_keys：均生效（busy_timeout 先于 WAL 切换设置）。
- user_version 0→1 迁移框架：单事务；高于当前版本直接报错；空库迁移与重复启动幂等均有测试。
- FTS5 trigram：独立虚拟表，与主表写入/删除在同一 IMMEDIATE 事务同步；
  启动不一致时单快照校验后 rebuild；1–2 字及纯标点回退 LIKE（转义齐全）。
- 并发：5 线程 × 20 = 100 次写入 + 100 次查询，无 `database is locked`；
  重启后 100 条一致；`PRAGMA integrity_check` = ok。

## 偏差（正式记录）

**并发模型**：任务原文为「单写线程 + channel」，实际为「短生命周期多连接 + 写事务串行」：
- 剪贴板入库（高频写）仍由监听线程独占长连接，等价于单写线程；
- 置顶/删除（低频 UI 写）走短连接 + `BEGIN IMMEDIATE`，由 SQLite 写锁排队 + busy_timeout 串行；
- 读连接短生命周期（只读），`Connection` 与锁不跨 await。
背景原因：原 `BEGIN DEFERRED` 在多连接下先持 SHARED 再升级写锁会死锁（不触发 busy handler），
已改为 IMMEDIATE。评审确认该偏差可接受。

**schema 范围**：见 ADR-0014。

## 遗留建议（不阻塞）

1. `open_readonly_at` 实际可写、可迁移，名不副实；后续触碰时改名（如 `open_reader_at`）。
2. 并发双删同一 id 时第二个 delete 静默成功（存在性检查在事务外），无损坏，可改为事务内 `changes()` 判断。
3. 「多线程同时对空库首开」测试缺位；busy_timeout 前置后风险低。
