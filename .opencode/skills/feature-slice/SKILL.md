# 任务切片流程

本技能定义 QuickWin 的**单任务工作流**。目标：一次只交付一个可验收的切片，不留半成品。

## 何时使用

- 用户说「继续」「做下一个任务」「实现 X 功能」「修这个 bug」。
- 需要判断「现在该做什么」「这个任务算不算完成」。
- 不要用于纯文档讨论或方案评审（那属于 plan 模式）。

## 输入

1. `TASKS.md` 的当前焦点与任务条目。
2. 任务对应的规格：`docs/SPEC.md` → `docs/ARCHITECTURE.md` → `docs/WIN32-NOTES.md`。
3. `AGENTS.md` 第 2 节硬规则、第 9 节 DoD。

## 选任务规则

按顺序取**第一个**满足条件的任务：

1. 状态为 `[!]` 且阻塞已解除 → 优先恢复。
2. 状态为 `[ ]`，且「依赖」全部为 `[x]`。
3. 属于「当前焦点」里程碑。
4. 早于其他里程碑（M0 未完成不跳 M2）。

不满足以上条件时停下来问用户，不要自行跳到后置任务或需求池。

## 流程

### 1. 判断任务复杂度与评审级别

检查 `TASKS.md` 中任务条目的标记：

- **`[L0]`**：轻量任务（纯文档、测试补全、文案、配置），实现者自验即可，跳过第 7 步评审。
- **`[L1]`**（默认）：标准任务（单模块业务逻辑），1 轮外部评审。
- **`[L2]`** 或 **`[complex]`**：严格任务（跨模块、Win32 边界、安全），设计评审 + 实现评审，最多 2 轮。

如果任务无标记，按以下规则判断级别：
- 只改 `docs/`、`*.test.ts`、`tests/` → L0
- 只改单个 `services/` 或 `commands/` 模块 → L1
- 涉及多个模块交互、`platform/` Win32 边界、新增依赖 → L2

### 1.5 复杂任务：mini-design（仅 L2 / `[complex]` 任务）

**目的**：在动手前理清思路，暴露风险，避免返工。

**mini-design 模板**（3-5 行，写到 `docs/reviews/T-<id>-design.md`）：

```markdown
# T-<id> mini-design

## 改动文件
- `src-tauri/src/services/xxx.rs`（新增）
- `src-tauri/src/commands/xxx.rs`（修改）

## 模块交互
commands::xxx → services::xxx → platform::xxx

## 错误处理
- 场景 1：xxx → 返回 `AppError::Xxx`，前端显示"xxx"
- 场景 2：xxx → 降级为 xxx

## 测试策略
- 单测：覆盖 xxx 场景
- 手测：xxx 应用，验证 xxx 行为
```

**设计自检流程**（优先自检，减少外部评审轮次）：

1. 实现模型自检以下清单：
   - [ ] 是否新增依赖？→ 需要 ADR
   - [ ] 是否改目录结构？→ 需要 ADR
   - [ ] 是否改 IPC 契约？→ 需要更新 `ipc.ts` + 契约测试
   - [ ] 是否涉及 Win32 边界？→ 需要读 WIN32-NOTES 对应章节
   - [ ] 以上全否 → 设计自检通过，直接进入实现

2. 若自检发现需要 ADR 或涉及架构变更，用 `subagent` 调用评审模型（固定 `zai-org/glm-5`），提示词：

```
你是 QuickWin 的设计评审员。请审查以下 mini-design，指出最大风险并给出改进建议。

任务：T-<id> <任务名称>
验收标准：<从 TASKS.md 复制>

mini-design：
<粘贴 mini-design 内容>

输出格式（最多 3 条）：
[BLOCKER] 风险标题
- 问题：xxx
- 建议：xxx

[NONBLOCK] 建议标题
- 说明：xxx

结论：PASS / FAIL
```

3. 评审结论处理：
   - `PASS` → 继续实现。
   - `FAIL` → 修改 mini-design，重新评审（最多 2 轮）。第 2 轮仍 FAIL → 标 `[!]` 并问用户。

4. 评审记录写入 `docs/reviews/T-<id>-design.md`。

### 2. 声明计划（先说话再动手）

一句话说明：

```
任务：T-206 保留策略与容量治理
改动：services/storage/retention.rs（新增）、storage/migrations.rs（不改）、TASKS.md
验证：cargo test retention + 改系统时间手测（清单见任务）
```

如果发现验收标准有歧义，先问，不要猜。

### 3. 读规格

只读该任务相关的章节，避免把整份 PRD 塞进上下文。读完后确认三个东西：

- 行为（输入 → 输出）
- 边界（空、超长、失败、权限）
- 验收（如何证明做完了）

### 4. 实现最小切片

- 只改任务需要的文件；顺手发现的问题记到 `TASKS.md` 需求池，不现场修。
- 先写核心纯函数 + 测试，再接 UI/IPC。
- 涉及 Win32 时加载 `tauri-win32` 技能，严格按其中的模板与清单。
- 不新增依赖；确需新增时先在 `docs/DECISIONS.md` 写 ADR 并告知用户。

### 5. 写测试

**最小测试集**（必须覆盖）：
- 核心纯函数的**正常路径 + 1 个边界 + 1 个反例**
- 数据库操作：**成功 + 失败 + 幂等**
- 前端交互：**键盘导航 + 错误提示**

**可选测试**（时间充裕时补）：
- 判定表的每一行
- 多个边界条件
- 性能基准测试

测试名用中文描述行为。

### 6. 验证

按改动范围选择质量门（详见 `.opencode/commands/verify.md`）：

| 改动范围 | 命令 |
|---------|------|
| 跨端改动 | `npm.cmd run verify` |
| 仅前端（`src/`） | `npm.cmd run verify:fe` |
| 仅后端（`src-tauri/`） | `npm.cmd run verify:be` |
| 纯文档（L0） | 不运行，自验即可 |

失败就修到绿。禁止：

- 删除失败测试、`#[ignore]`、跳过 lint。
- 放宽断言来「通过」。
- 只跑自己改的那一个测试就宣称完成。

涉及 `platform/` 的，再按 `docs/WIN32-NOTES.md` 第 10 节跑对应条目，并记录：

```
手测：Win11 26200 / 150% / 双屏
结果：记事本/VS Code/Chrome 粘贴通过；管理员窗口提示正确
```

### 7. 交叉模型评审（提交门禁）

**触发**：按任务评审级别执行（见第 1 步）。L0 跳过本步，L1/L2 必须执行。

**材料**（只给事实，不给你的结论）：

- 任务 ID + 验收标准原文（从 `TASKS.md` 复制，不要转述）
- `git diff`（或改动文件清单 + 完整文件内容，未初始化 git 时用后者）
- `npm.cmd run verify` 的分项结果（按改动范围选择 `verify` / `verify:fe` / `verify:be`）
- 相关规格章节：`docs/SPEC.md` / `ARCHITECTURE.md` / `WIN32-NOTES.md`
- 如果是 L2 / `[complex]` 任务，附上 mini-design 评审记录 `docs/reviews/T-<id>-design.md`

禁止把「我觉得这样最合理」「已验证没问题」写进给评审模型的输入——会污染判断。

**执行**：用 `subagent`，`agent: general`，`model: zai-org/glm-5`（固定评审模型，减少标准差异），提示词：

```
你是 QuickWin 的代码评审员。请审查以下实现，按 BLOCKER / NONBLOCK 分类给出意见。

任务：T-<id> <任务名称>
评审级别：L1 / L2
验收标准：<从 TASKS.md 复制>

改动：
<粘贴 git diff 或文件内容>

verify 结果：
<粘贴 verify 输出>

输出格式（最多 5 条 BLOCKER + 5 条 NONBLOCK）：
[BLOCKER] 文件名:行号 - 问题描述 - 修复建议
[NONBLOCK] 文件名:行号 - 问题描述 - 建议

结论：PASS / FAIL
```

评审者只读，不得改文件、不得执行修改性命令。

**结论处理**（最多 2 轮）：

- **第 1 轮**：
  - `PASS` → 进入第 8 步。
  - `FAIL` → 只修 BLOCKER 项，NONBLOCK 登记到 `TASKS.md` 实现备注的「遗留」段，重新 `verify` + 重评。
- **第 2 轮**：
  - 只验证第 1 轮 BLOCKER 是否修复，不再提新问题。
  - 第 2 轮发现新问题 → 登记遗留，不打回（除非是数据丢失/安全级别）。
  - 结论为 `PASS` → 进入第 8 步。
- 模型报错/超时 → 标 `[!]`，写「交叉评审未执行」，不得静默放行。

**记录**（写入 `docs/reviews/T-<id>.md`）：

```markdown
# T-<id> <任务名称>

**实现模型**：qwen3.7-plus
**评审模型**：GLM5.3（固定）
**评审级别**：L1 / L2
**评审日期**：2026-10-26
**评审轮次**：1 / 2
**结论**：PASS

## BLOCKER（已修复）

1. **问题标题**（文件名:行号）
   - 问题：xxx
   - 修复：xxx
   - 验证：xxx

## NONBLOCK（登记遗留）

1. **建议标题**（文件名:行号）
   - 建议：xxx
   - 处理：登记到 TASKS.md 实现备注

## 遗留建议

- xxx
```

同时在 `TASKS.md` 该任务下记录：

```
交叉评审：GLM5.3（2026-10-26）PASS（L1，1 轮），详见 docs/reviews/T-<id>.md
```

### 8. 回写进度

更新 `TASKS.md`：

- `[ ]` → `[x]`，补日期。
- 有偏差时加「实现备注」：为什么偏离、留下了什么。
- 发现后续工作 → 加到「需求池」，不塞进当前任务。

### 9. 汇报

```
完成 T-206（2026-10-26）
改动：3 个文件（列路径）
验证：verify 绿；cargo test 12 项；手测 4 项
评审级别：L1
交叉评审：GLM5.3 PASS（1 轮），详见 docs/reviews/T-206.md
遗留：blob 回收在 Windows 文件锁下偶发失败，已记录到需求池
下一步建议：T-207 排除应用
```

L0 任务汇报模板：
```
完成 T-208（2026-10-26）
改动：2 个文件（列路径）
验证：verify 绿；L0 自验
下一步建议：T-301 应用索引
```

## 里程碑门禁

| 里程碑 | 进入下一阶段前必须 |
|---|---|
| M0 | `tauri:dev` 能起窗口，`verify` 绿 |
| M1 | 热键呼出/隐藏、焦点恢复、DB 读写、SendInput 全部手工验证 |
| M2 | 复制 20 条→搜索→粘贴端到端通过，TTL 手测通过 |
| M3 | 应用命中率抽查 ≥90%，`g`/`=` 可用 |
| M4 | 10 万文件索引不卡 UI，中文文件名可搜 |
| M5 | 4 个应用取词与替换通过，检测表单测覆盖 |
| M6 | 设置页全项可保存，新用户引导可完成 |
| M7 | 干净 Win11 安装→使用→卸载全流程 |

## 失败与阻塞

- 第一次失败：自己定位并修，最多两轮。
- 第二轮仍失败：把任务标 `[!]`，写清「现象 / 已排查 / 需要什么决策」，然后停下问用户。
- 不要为了绕过问题去改架构或放宽验收；那属于新决策，需要 ADR + 用户同意。

## 反模式（禁止）

- 一次开三个任务，最后一个都没验收。
- 先写 UI 再补核心逻辑（顺序反了会导致返工）。
- 把「暂时注释掉测试」当作修好。
- 在没有手动验证的情况下勾选 Win32 相关任务。
- 改完不回写 `TASKS.md`，让下一个人/下一次会话重新猜进度。
- 把需求池功能顺手做了。
